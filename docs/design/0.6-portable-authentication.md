# 0.6 portable authentication and browser logout

Design decision: 2026-10-14. The maintainer requests both certified/BLS and
enrolled Ed25519 admission, one shared session flow, and browser-driven logout
across independently hosted project canisters. The issuer-call experiment is
not the selected multi-subnet architecture. This document extends the
[ownership design](extraction.md) and [session contract](../sessions.md).

**Status:** design contract, not an implemented TEE capability. Maintained code
currently admits certified tokens; local Ed25519 signing, its portable credential
contract, protected key enrollment and browser logout fan-out are not production
features. Experimental signature timings do not qualify those missing pieces.
The review resolutions below select protocol behavior; they are not findings of
implementation vulnerabilities. The normative [protocol contract](0.6-auth-protocol.md)
fixes identity, signed encoding, revocation, ordering and reset behavior. The
[issuer enrollment and custody contract](0.6-tee-enrollment.md) defines trusted
governance, volatile key rotation and optional TEE assurance. The simplification
below supersedes earlier universal TEE/controller restrictions.
Implementation must match these contracts and qualify their acceptance cases
before claiming either the new protocol or the proposed Canic flag is supported.
Implementation and acceptance remain in [Auth #59](https://github.com/dragginzgame/ic-auth/issues/59)
and [Canic #491](https://github.com/dragginzgame/canic/issues/491), with Toko browser
adoption in [Toko #1803](https://github.com/dragginzgame/toko/issues/1803).

Uppercase MUST, MUST NOT and SHOULD are normative RFC 2119/RFC 8174 requirements.
The protocol and enrollment companions supply the detailed acceptance rules.

## Goals and limits

A browser logs in once, obtains a credential bound to a fresh browser signing
identity, and presents that same credential to any participating receiver allowed
by its signed audience and protected receiver policy. Each receiver explicitly
establishes its own session. Subsequent application calls use that identity and
local session checks; they do not carry a token or call an issuer.

Here the browser identity is a fresh Ed25519 key's self-authenticating principal,
used as the ingress sender directly. It is not a fresh delegated key acting as
the same stable account principal. Account authentication binds that browser
principal to a separate issuer-authenticated account subject. Two devices use
different principals and cannot overwrite each other's caller-keyed sessions.
The independent wallet service may still issue stable-principal ingress
delegations; that is not this application's session identity contract.

Project instances can reside on different subnets. No routine session admission
or authorization requires receiver-to-issuer or receiver-to-receiver calls.
Browser-to-canister calls still incur ingress and execution costs. Administrative
issuer enrollment and revocation distribution are separate control-plane work.
There is no promise that arbitrary IC canisters trust this credential, that one
verification establishes all sessions, or that authentication grants resources.

TEE support must not make non-TEE deployment or ordinary local testing unusable.
Both proof mechanisms remain intentional supported choices, not compatibility
fallbacks. Neither revives the retired per-call token guard or online issuer
admission. One mechanism is selected by protected issuer policy; request fields
cannot choose a weaker verifier after another verifier rejects the request.

## Choose the authentication requirement first

An application that only needs an authenticated IC caller and its own account
mapping should use ingress authentication and application policy directly. It
need not adopt a portable issuer credential. This is a workflow decision, not a
fallback that bypasses verification on an endpoint requiring portable identity.

Portable credentials are useful when independently verifying canisters need an
approved issuer's binding between a browser principal and an account. For that
workflow, authenticate issuer enrollment once per key/refresh and use cheap
Ed25519 verification per admission, followed by ordinary session checks. Expensive
proofs must justify their added assurance or portability; they do not make trusted
controllers honest. Keep finite authority, replay and logout rules in either
portable mechanism. Cost comparisons must include enrollment/rotation as well as
user issuance and admission.

## Wallet account authentication

Solana and Ethereum login will use an IC Auth-owned challenge format and wallet
adapters, without SIWS or SIWE protocols or dependencies.
Reuse established signature primitives and supported wallet message-signing APIs;
do not invent cryptography or ask users to sign transactions for authentication.

The issuer prepares a bounded, single-use challenge binding its configured
application/domain, wallet network and address/key, fresh browser public key,
nonce and issue/expiry times. It verifies the exact expected signed bytes and
atomically consumes the challenge when binding the browser login to an account.
Client-provided domain text does not authenticate the browser's origin. Freeze
the wallet challenge encoding, wallet-specific signing envelopes, verification
rules and retry behavior separately before implementation; the portable
credential schema does not define this earlier account-authentication step.

**Wallet-origin review gate:** custom domain text alone does not prevent a relay
phish. An attacker can obtain a legitimate-domain challenge bound to its own
browser key and persuade a victim to sign it elsewhere. The issuer cannot infer
the signing page's origin from that signature. Production wallet login MUST NOT
claim phishing-resistant origin binding on this basis.

The proposed Ethereum correction is ERC-4361-compatible text, generated and
verified by our own bounded implementation without a SIWE library dependency.
This is still adoption of the ERC-4361 message standard and would revise the
maintainer's earlier no-SIWE-protocol choice; approval is pending. Its nonce,
domain/URI, chain, times and resource/request binding must include the browser
key and exact registered application. MetaMask recognizes that format and warns
on domain mismatch, but users can override the warning. Qualification MUST test
the actual wallet display, mismatch behavior and rejection cases; no guarantee
extends to unsupported wallets. See [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361)
and [MetaMask domain binding](https://docs.metamask.io/metamask-connect/evm/guides/sign-data/siwe/).
Solana custom-message origin/consent behavior requires its own wallet-specific
qualification; Ethereum's warning does not establish Solana protection. Wallet
format/origin policy is not frozen while this decision remains outstanding.

The first Ethereum adapter targets ordinary externally owned accounts. Contract
wallet authentication needs a separate chain-state validation contract and is
not implied by support for ordinary signatures. Wallet linking and resource
ownership remain application policy. Neither wallet signature is sent on every
application call: successful account authentication feeds the same portable
credential and receiver session flow below.

Wallet choice, credential mechanism and receiver session storage are independent.
Memory hosts omit durable session restoration and require fresh account login
after reset under the signed login-start cutoff. Persistent hosts may retain
valid sessions across normal upgrades, subject to their original deadlines and
fresh protected authority. Neither setting determines account-record persistence,
browser key custody or issuer private-key storage. See the normative
[reset matrix](0.6-auth-protocol.md#enrollment-and-restoration).

## One session flow, two admission mechanisms

| Property | Certified/BLS | Enrolled Ed25519 |
| --- | --- | --- |
| Issuer proof | Existing IC-certified token machinery | Credential signed by the enrolled issuer key |
| Issuer hosting | Ordinary compatible IC subnet | Explicit custody policy: trusted ordinary deployment, qualified TEE, or threshold signer |
| Destination hosting | Ordinary or confidential subnet | Ordinary or confidential subnet |
| First use on a receiver | Verify portable certification and claims | Verify enrolled issuer key, signature and claims |
| Later calls | Shared caller-bound session checks | Same session checks |
| Local tests | Real local certification | Real software Ed25519 signing and verification; no hardware confidentiality claim |

Both verifiers must enter one canonical checked admission/transaction path.
Preserve caller binding, audience, scope narrowing, protected authority generation,
expiry, reset floor, replay retention, capacity and admission work budgets.
Do not introduce an unchecked public session constructor or duplicate the session
store, ordinary endpoint guards, renewal and logout logic for each algorithm.
The session record now retains portable issuer/account and enrollment bindings.
Its new storage discriminator rejects the old token-specific record encoding.
The shared engine accepts both complete verifiers without dummy Root authority.
Production Candid/client adoption and retained-state retirement remain consumer
requirements; see [the session contract](../sessions.md).

For Ed25519, Auth owns the domain-separated canonical signed claims and strict
signature verification using an established primitive. Required authenticated
facts include issuer/key identity, application trust domain, browser principal,
login identity, issuance/expiry, permitted audience, scopes and unique credential
identity. Keep bounds explicit. Pin the expected algorithm and key from protected
authority; do not trust an embedded public key or a client assertion of TEE status.
Bind the absolute login authorization deadline into the signed credential as well.

Canic owns issuer enrollment, topology, permitted grants and deployment evidence.
The protocol distinguishes monotonic enrollment revision, authority generation,
snapshot freshness and key validity. Both admission and existing-session use
refuse expired enrollment. Refresh never extends a stored session lease.
Enrollment updates come from the installed authority, not from user claims;
older snapshots cannot undo revocation, including after restart/restore. See
[enrollment and reset rules](0.6-auth-protocol.md#enrollment-and-restoration).
No BLS proof or attestation is verified anew for every Ed25519 user credential.
Unknown/stale keys refuse locally without a request-path enrollment fetch.

The selected local-key lifecycle uses IC randomness, heap-only Ed25519 keys and
fresh enrollment after every issuer code upgrade. Root authenticates and approves
the issuer key; a chain-key authorization can make that enrollment portable.
Receivers cache protected enrollment rather than repeat expensive Root proofs for
every user. Heap-only storage reduces persistence mistakes, but snapshots can
still copy heap secrets. Governance is trusted for both local and chain-key
signing. TEE is an optional confidentiality policy, not a prerequisite for this
receiver flow. See the [custody contract](0.6-tee-enrollment.md).

## Issuer signing alternatives and decision evidence

Ed25519 verification does not require a locally held private key. IC threshold
Schnorr can produce Ed25519 signatures with distributed key shares rather than
an extractable complete key in issuer memory. It does not require a TEE issuer.
For a direct credential signature this is wire-compatible: sign the identical
32-byte SHA-256 claims digest as an ordinary Ed25519 message, and retain the same
claims, signature envelope and receiver verifier. Custody/enrollment policy
MUST distinguish this authority from a locally generated key. A malicious
issuer controller can still replace code to request unauthorized signatures,
even though it cannot download the threshold key. See
[chain-key cryptography](https://docs.internetcomputer.org/concepts/chain-key-cryptography/).

| Issuance candidate | Receiver work | Tradeoff and current disposition |
| --- | --- | --- |
| Local volatile signing | Enrolled Ed25519 verification | Selected lifecycle candidate; avoids per-credential management signing, trusts governance and an explicit replica-confidentiality policy; TEE protection is optional, full costs unmeasured |
| Threshold Schnorr per credential | Enrolled Ed25519 verification | Strong alternative without local complete-key custody; adds a paid asynchronous management call per issuance/renewal, not per receiver admission; must benchmark cost, queueing and latency |
| Threshold signature over a batch root | Ed25519 plus bounded Merkle membership | Amortizes signing across actual batch occupancy; needs batch waiting, exact domain/leaf/root encoding, inclusion proof bounds and logout-safe asynchronous publication; not the frozen direct-signature envelope |

A tutorial's 25B cycles attached to a call is not a measured burn or universal
tariff. Use the selected key's current platform fee/cost API and actual cycle
deductions; [current cycle pricing](https://docs.internetcomputer.org/references/cycle-costs/)
varies by signing key/subnet. For issuance rate `r`, charged signature cost `C`
and effective batch occupancy `b`, signing-only burn is approximately `r*C` or
`r*C/b`, plus queue/storage/transport costs. Qualification MUST include sparse
traffic, renewal peaks and aborted/late batches, not only full batches. Batches
must recheck login revocation after signing awaits before publishing credentials.

Threshold signing is deferred for measurement, not rejected as necessarily slower
overall or less scalable. Local signing MUST NOT be presented as proven superior
before complete issuance/admission/renewal comparisons and custody qualification.
A batch alternative needs an explicit protocol revision, never reinterpretation
of the existing direct-signature tag. This review does not add a third live flow.

## Canic feature selection

The requested opt-in Cargo feature is proposed as `auth-tee`; this name is a
design target, **not an available flag**. It selects optional TEE custody
integration when implemented, rather than being required for all Ed25519
verification. Keep default certified/BLS
admission available without it. Receiver-only roles need an Ed25519 verification
capability, not issuer signing, secret storage, attestation machinery or TEE
hosting. Canic must validate each generated canister's resolved feature graph.

New issuer key generation, local signing and heap-key lifecycle MUST live in a
separate issuer crate, with no dependency edge from the receiver verifier/session
crate to that issuer crate. Shared passive types and canonical encoding contain
no secret custody. This is a required package boundary, not a new published crate
or implemented feature today. Cargo features alone are insufficient because
workspace builds can unify dependency features. Qualification MUST inspect both
workspace and per-canister package builds, dependency edges and final artifacts;
separate crates prevent automatic linkage only when the dependency graph obeys
this boundary. Consumer configuration remains Canic-owned.

Build availability and trusted runtime policy are distinct. Proposed host-side
TOML selection under the owning auth configuration is
`credential_mode = "certified"` or `credential_mode = "enrolled_ed25519"`.
Issuer custody is a separate protected choice: local volatile key with an explicit
operator-trust policy, qualified TEE local custody, or threshold signing. These
config names are proposed contracts, not implemented options.
The exact config location and generated types belong to Canic. Reject unsupported
feature/config combinations. A build containing both verifiers does not authorize
both algorithms for every issuer; bind each enrolled issuer/key to its configured
mechanism. Production TEE mode must refuse activation without admitted deployment
evidence. A boolean in a config file cannot establish hardware confidentiality.

The pending codec's `PortableMechanism::Ed25519`/wire tag 1 keeps its exact
meaning across approved custody choices; changing custody never changes signed
bytes implicitly. The old proposed `tee_signed` configuration name is withdrawn.
Browser keys remain Ed25519 in this schema. P-256 would require a separately
reviewed key/DER/caller-binding format and is not currently supported.

Selection does not change the browser's session-establishment API or application
endpoint guards. Memory versus persistent session storage remains the independent
[host storage choice](../sessions.md#storage-selection-and-upgrade-contract-for-06).
Disabling TEE must not silently reinterpret keys, credentials or stored sessions.
Canic's release/reset rules govern its own deployment; standalone IC Auth hosts
retain their own identity, storage and recovery obligations.

## Login, renewal and logout

Each login is identified by its fresh browser principal within the installed
application trust domain. Its issuer-authenticated start and absolute deadline
are immutable across renewals. Renewal credentials have distinct identities and
cannot exceed that deadline or approved authority validity. A fresh login needs
account authentication and a fresh key; possession of the old browser key alone
cannot create another login. Account-wide/all-device revocation is separate.

The client ensures admission separately per receiver, browser identity and grants.
It records a destination before dispatching establishment so a lost reply cannot
hide a session from later logout. It retains this bounded destination inventory
across reloads, without silently evicting still-live entries; at capacity, refuse
additional admissions or explicitly retire entries after their possible expiry.
Knowledge of a local session is an optimization; receivers always authorize.
Application mutations with uncertain outcomes must not be blindly retried.

Distinguish the proof's admission window, the admitted session lease and the
login's absolute authorization deadline. Current code admits proofs with at most
60 seconds of lifetime but permits sessions up to 1800 seconds under host policy;
it intentionally allows sessions to outlive their admission proofs. Earlier
discussion requiring every session to expire with the proof was too strict and
would increase verification frequency. This design preserves separate lifetimes.

Active users can renew while the issuer's protected browser binding remains
eligible. A session lease is capped by protected receiver policy, the signed
login authorization deadline and accepted key/authority validity. Proof expiry
prevents new admission; session expiry prevents continued use. Ordinary activity
does not silently extend either. Long-lived UI login uses explicit renewal;
this does not require a wallet prompt at every destination. Both mechanisms need
the same authenticated login deadline contract; it is not a field the present
token/session API already provides. Choose limits from measured load and the
accepted revocation window, not an unqualified universal duration.

On logout the browser:

1. Durably marks the login as logging out and advances its local generation in
   one browser-storage transaction before network fan-out. All signing and
   callback paths consult this state; notification alone is insufficient.
2. Sends authenticated, idempotent revocation updates to the issuer and every
   recorded receiver, including the current project, with bounded concurrency.
   Requests target canisters, not entire subnets. No receiver fans out via ICCs.
3. Waits for a bounded confirmation window, distinguishes confirmed revocation
   from unknown outcomes, then clears usable browser credentials and session keys.
   Local logout must complete even when a destination is unreachable.

The window MUST cover known outstanding proof admission windows with qualified
clock margins. `Capacity` for a not-yet-admitted principal triggers bounded retries:
late establishment reserves a slot for the next logout. Proof expiry by itself
cannot prove logout, because a session may have committed just before it. Apply
the [browser retry contract](../browser-client.md#planned-06-logout-retries),
including final attempts, fixed key-deletion deadline and explicit unknown state
when issuer revocation or receiver confirmation fails.

The issuer revokes renewal and each receiver revokes the authenticated caller's
browser principal. The fixed [logout request/result](0.6-auth-protocol.md#logout)
requires no admission credential or issuer-key verification. It works with no
session, expired proofs and retired keys. A bounded tombstone blocks all later
credentials for that principal, including establishment overtaken by logout.
Success linearizes at the synchronous revocation commit. Issuance rechecks
authority after awaits, and application workflows must recheck before new
privileged effects after an await; already-dispatched effects may still finish.
See [ordering](0.6-auth-protocol.md#ordering-and-in-flight-work).

Do not acknowledge remote revocation if its tombstone cannot be retained safely.
The protocol fixes separate capacity for logout-before-admission and reserved
capacity for admitted callers. Persistent normal upgrades retain tombstones.
Memory mode instead rejects every pre-reset login by its immutable signed login
start with the qualified cross-subnet clock margin, even when a newly issued
renewal proof has a later issuance time. Every such upgrade requires returning
users to authenticate again, potentially prompting their wallet; this is an
explicit deploy-cadence cost. Persistent normal upgrades avoid that reset. Memory
mode does not need durable session/tombstone storage. Recovery from an old backup follows
that same invalidation rule. Authority enrollment always reboots closed pending
an authenticated fresh snapshot. These are definite per-profile rules, not a
choice left to individual call sites; see the protocol's reset matrix.

After key deletion, retaining a retry queue alone does not confer authority to
send future logout calls. The baseline promises bounded attempts and expiry,
not indefinite background retries or retaining a usable login key until every
destination answers. A separately verifiable, revocation-only receipt could
permit later relay, but is not part of this design's implemented contract.

| Result | Honest guarantee |
| --- | --- |
| Browser credentials removed | This browser stops using the login; another retained/stolen key is not erased |
| Receiver confirms logout | This login cannot authorize or re-establish there before its revocation record expires |
| Issuer confirms logout | No further credentials/renewal for this login; already-issued proofs remain usable at uninformed destinations |
| Destination is offline or missing from inventory | Existing leases expire and each proof expires; replacement proofs remain obtainable until the login deadline if issuer revocation did not succeed |
| All-device logout requested | Separate account-level operation requiring coordination beyond this browser's inventory |

A valid proof plus its bound browser private key can still admit on an allowed
but unvisited destination until proof expiry if that destination has not learned
of revocation. Its resulting session can outlive that proof. After confirmed
issuer revocation, the conservative residual duration is explicitly:

`min(D, A, max(R, P + L)) + Delta`

Expanded without abbreviations:
`min(remaining_login_deadline, nonextendable_authority_validity, max(remaining_session, remaining_proof_window + max_lease)) + clock_skew`.

All terms are durations from the same observation time, with elapsed deadlines
clamped to zero: `D` is remaining absolute login lifetime, `R` the greatest
remaining existing lease, `P` the greatest remaining already-issued proof window,
and `L` the maximum receiver lease. `A` is a nonextendable remaining authority
validity bound; use infinity if authority can refresh beyond the observed window,
not today's snapshot freshness as an immutable bound. `Delta` is the qualified
clock uncertainty margin, not permission to accept expired credentials. This is
`max(R, P + L)`, never `max(R, P) + L`. If issuer revocation also
fails, a retained key may renew until the finite absolute login deadline.
This is the unavoidable remaining window with offline verification.
TEE does not change it. Browser key deletion usually makes leftover sessions
unusable locally, but is not a guarantee against stolen keys or other devices.

## Browser origin and key custody

0.6 supports one trusted top-level frontend origin/storage partition for a shared
login, including many backend canisters on different subnets. Separate frontend
origins have separate logins; cross-origin SSO/signing brokers are out of scope.
Do not export the login key to project origins or accept arbitrary cross-origin
signing messages. BroadcastChannel is a notification optimization with
[origin/partition restrictions](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API),
not the authoritative logout state.

The origin-owned key/storage adapter uses a non-exportable signing handle where
supported and never stores unencrypted raw key bytes for convenience. This does
not protect against malicious code executing within the trusted origin. Persist
login generation, logout state and receiver inventory atomically in the same
origin-owned database; refuse persistent-login activation if the required
storage/key adapter is unavailable. No silent memory fallback for this profile.
Missing/deleted durable state means logged out, never reconstruct an active login
from a cached key. If the logout transaction fails, stop this tab's activity and
report durable cleanup failure; do not claim that other tabs were invalidated.

Before signing, resuming a suspended tab or applying an asynchronous callback,
read the durable generation/state and require an active matching login. A browser
crash after the logout transaction must reopen into logged-out cleanup, never
active login. Surviving bounded attempts may use only revocation signing; startup
must not extend the saved cleanup deadline. Clear the key by that deadline or
immediately on recovery if it passed. A request already signed/dispatched before
the logout transaction can still arrive; receiver tombstones and server ordering
handle that race. Notifications cannot cancel already-signed ingress messages.

## Local development without TEE

Ordinary developer machines and CI must exercise both mechanisms using published
IC Testkit. Real Ed25519 software signing uses the same canonical bytes, verifier
and session path as production. Only the environment's key-protection assurance
is substituted. No new PocketIC dependency or alternate cryptographic primitive
is required. Local entropy/key fixtures never become production secrets.

Local tests need no TEE and make no hardware confidentiality claim. Production
local-key deployments must explicitly select and approve their custody assumptions.
A deployment requiring TEE MUST refuse activation without the required evidence;
it cannot silently fall back to the ordinary-subnet trust profile. Browser requests
cannot select or weaken custody policy. Test those refusals separately from local
functional success, and test receivers on ordinary simulated subnets.

Local tests can prove protocol correctness, signatures, signed ingress, expiry,
replay, session isolation, reset behavior and browser orchestration. They cannot
prove hardware secrecy, firmware patch status, actual attestation, secure node
replacement/recovery, production throughput or cross-subnet latency. A real
confidential deployment needs a separate security/operational acceptance record.
Mainnet/paid deployment remains a separately authorized action.

## Capacity and abuse

Existing isolated measurements are decision evidence, not production SLAs:

| Measurement | Observed local cycles | Scope |
| --- | --- | --- |
| Certified cold session admission | About 498M | Full fixture admission, size-optimized Wasm |
| Ed25519 primitive verification update | About 10.4M | Installed public key and small message, not full admission |
| Complete Ed25519 portable admission | 12.68–12.95M | Current volatile receiver fixture, six successful admissions across two runs and two receivers/devices |
| Ordinary session-authorized update | About 7M | Fixture call including platform charges |
| Local issuer signing and complete login flow | Unmeasured | Requires implementation and qualification |

The 2026-10-15 complete Ed25519 probe records canister cycle-balance deltas around
the existing real update endpoints, including decoding, verification, shared
session/replay/revocation work, response encoding and platform charges. Its other
observations were 10,586,084 cycles for a forged signature, 10,088,836 for an exact
retry after proof expiry, 7,217,743 for admitted logout and 7,181,155 for an ordinary
session-authorized update. Invalid admission is checked not to create a session.
Signing occurs in the native test producer and is excluded; this measures neither
wallet login nor production issuer/enrollment, durable writes or network latency.
The combined qualification Wasm is 1,982,443 bytes, SHA-256
`a359b1861157e9db0323d7d6f220b3b77e78856595d1b123d55ce66a1c683cbc`;
it contains other qualification endpoints and is not a minimal receiver-size probe.
Reproduce with `make test-qualification`; output reports the selected artifact hash
and each cycle delta. Initial evidence is `target/portable-cost-qualification.log`.
These few samples are diagnostic, not a throughput distribution or performance SLA.
The complete-gate repeat in `target/portable-cost-ci.log` used the same Wasm and
observed fresh admissions of 12,681,007 / 12,681,007 / 12,932,916 cycles; forged
rejection was 10,586,098, with unchanged retry/ordinary-update/logout deltas.
The older certified result used a different fixture: a matching complete certified
admission benchmark remains necessary before claiming a percentage saving.

Sources and sealed artifacts are recorded in
[the signature experiment](https://github.com/dragginzgame/ic-auth/issues/59#issuecomment-6165276123)
and [the admission experiment](https://github.com/dragginzgame/ic-auth/issues/59#issuecomment-6163232483).
Do not quote the ratio between primitive verification and full admission as the
production saving. Hardware isolation itself does not accelerate BLS mathematics.
Enrolled Ed25519 keys provide the cheaper candidate verification mechanism; TEE
changes key custody rather than the verifier mathematics.

Non-TEE capacity is a concern to measure, not a declaration that it cannot scale.
Estimate receiver work as fresh/renewal admissions times admission cost plus
ordinary calls times session-check cost, including rejected requests, decoding,
storage and application work. Fleet totals also depend on distinct destinations
per login and renewal frequency. Long-lived sessions amortize initial cost;
short revocation windows increase renewal/admission work. No fixed throughput or
expiry promise is justified by the current probes.

Both modes retain receiver-wide work budgets, bounded payload/state sizes and
issuance/renewal limits. Principal-only limits do not stop automated identities.
TEE does not prevent valid issuance abuse or provide free execution. Repeated
logout requests, unknown login tombstones and enrollment updates also need
bounded work/state; exhaustion must not break existing session authorization.

## Security and acceptance boundary

The trust boundary is approved issuer governance plus an explicit signing-key
custody policy. Controllers can abuse local or chain-key signing by changing the
application. A copied local key additionally permits off-network signing until
receivers stop accepting it; a threshold key is not present as a complete secret
in issuer memory. Volatile keys rotate on code upgrades, but cannot erase prior
copies. Finite enrollment, retirement and rollback protection therefore remain.

The [enrollment and custody contract](0.6-tee-enrollment.md) defines the common
lifecycle and optional TEE qualification. TEE does not remove controller trust,
provide instant revocation or solve browser logout propagation. Hardware evidence
is required for claims of protection from node operators, not for every workflow
using the shared portable verifier. No controller-call-path ban or universal NNS
watcher is required. Stronger deployment guarantees need their own evidence.

The release acceptance matrix must cover both proof mechanisms and both storage
modes: real signed ingress, wrong caller/issuer/key/algorithm/audience/scope,
tampering, expiry, replay/atomicity, reset and protected authority changes. Exercise
one credential on at least three receivers across two simulated subnets with no
admission ICC, followed by ordinary session calls. Prove local logout, cross-tab
logout, lost replies, offline receivers, late establishment/renewal after logout,
re-login with a fresh key, and independent sessions on another device. Include
browser restart and destination-inventory bounds. Hardware checks stay separate.
Also cover two simultaneous devices for one account, proofless logout after proof
expiry/key retirement, issuance paused across logout, post-await application
effects, revoked enrollment followed by an older signed snapshot and restart,
backup rollback, a crash mid-logout and a suspended tab resuming. Exact schema
vectors and both proof mechanisms must satisfy the same protocol acceptance.

| Review requirement | Required acceptance evidence |
| --- | --- |
| Governance and key lifecycle | Explicit trusted authority; heap-only local keys rotate on code upgrade; snapshots/restores cannot reactivate retired keys; disclosure triggers retirement |
| Optional TEE assurance | Qualify the selected hardware/confidentiality policy only when claimed; distinguish pre-change suspension from eventual detection, with no silent custody downgrade |
| Account namespace | Two issuers with the same subject remain distinct in session metadata and consumer account resolution |
| Root availability | Receiver-pulled jittered refresh, bounded outage retries, closed boot/stale enrollment, monotonic recovery without revived authority |
| Browser retry ordering | NotYetValid retries without grace; Capacity then late admission; proof expiry with a live session; unknown renewal and bounded key cleanup |
| Cross-subnet time | Qualified skew bound; issuer-ahead reset refuses old logins; overflow/bound failure closes admission; logout retention covers renewal through the absolute deadline |
| Logout capacity | Unknown-principal flood cannot consume admitted reservations; typed exhaustion, no eviction or false success |
| Wallet origin | Explicit message-format decision, exact key/application binding, relay/mismatch wallet UI tests and documented limitations |
| Package isolation | Workspace/per-package receiver artifacts and dependency graph exclude issuer custody code |
| Signing selection | Full issuance/renewal/admission costs and latency, including sparse threshold batches; no primitive-only speedup claim |

Measure complete issuance, cold admission, renewal, invalid admission, ordinary
calls and logout, with Wasm size, instruction counts, cycle deductions and
feature graphs for each actual artifact. The production TEE flag cannot be
advertised as supported until that path, enrollment and deployment checks exist.
Auth owns the reusable contracts; Canic owns feature/config/host integration;
Toko owns account binding, application policy and browser UX. GitHub issues own
implementation progress; this document is the shared design, not a task queue.
