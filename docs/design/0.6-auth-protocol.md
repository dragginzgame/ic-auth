# 0.6 application authentication protocol contract

Review resolution: 2026-10-14. This fixes the protocol decisions for the
[portable authentication design](0.6-portable-authentication.md). It describes
the implementation target; the paragraphs below distinguish implemented library
contracts from pending production adapters. The existing
token format must not be silently reinterpreted as this format. Implementation,
canonical vectors, codec generation and host qualification remain in
[Auth #59](https://github.com/dragginzgame/ic-auth/issues/59) and
[Canic #491](https://github.com/dragginzgame/canic/issues/491).

The pending implementation now provides passive `PortableClaims` and
`PortableMechanism` types plus `ic_auth::portable::{encode_claims, decode_claims,
claims_hash, browser_principal}` for the canonical claims domain below. Decoding
checks structural bounds, labels/order and nonanonymous account subject, not
time, signatures, caller possession, enrollment or authorization. These helpers
do not admit sessions. `validate_claims_context` separately checks protected
runtime caller, issuer/key/audience, grants, time windows, enrollment expiry and
reset floors for both mechanism tags. The optional Ed25519 verifier requires
that context and verifies the signature; neither helper authenticates enrollment
provenance or commits session/replay/revocation state. The `token-verification`
capability also exposes `portable_certified::verify_certified_claims`, reusing
the existing Root/delegation and IC signature verifiers with these shared checks.
It takes bounded claims, delegation and issuer signature as separate inputs.
Both verifiers require the same host-retained
`admission_budget::SessionAdmissionBudget`. Bounded shape/context refusals precede
charging; expensive signature verification spends credit even on failure. Hosts
must preserve charges on later storage failure and share the budget across
callers, mechanisms and endpoints. Recreating it starts empty. This limits fresh
cryptographic attempts, not ingress traffic or fairness. The shared session engine
now commits portable admission with replay and login revocation reservations.
Both verifiers return read-only `VerifiedPortableClaims`, with canonical fingerprint
and verification time; callers cannot construct it from decoded claims. It is
evidence for that protected snapshot, not durable authority or session admission.
Its `session_expires_at_ns` calculation requires a role from protected receiver
configuration and checks the requested scopes against that single signed grant.
It rejects absent roles and does not combine scopes from different roles. The
same request-narrowing owner serves the existing session engine. It then uses the
shared checked request TTL policy
and caps the lease at the signed login deadline and captured key/enrollment
expiry. Proof expiry only limits admission; refreshing enrollment cannot extend
an earlier result or a stored lease. The host must still commit under the same
protected snapshot and enforce current authority, replay and revocation.
The maintained session engine admits only portable claims through these complete
verifiers. It handles exact retries, current authority, scoped authorization and
caller-authenticated logout through one record and transaction contract. See
[the session API](../sessions.md). `PortableCredential` and `PortableProof` now
provide Rust-owned Candid data contracts, with generated browser descriptors.
`portable_credential::verify_credential` dispatches only against a protected
`PortableVerificationContext`; a request cannot select enrollment or a public key.
Production endpoint/browser orchestration, durable host integration and enrollment
lifecycle remain implementation work. The internal volatile receiver fixture is not a production service.

`MemoryLoginRevocations` implements bounded volatile reservation/tombstone
bookkeeping for one installed trust domain, supplied at construction. Reservation
requires the shared verified result, matching runtime caller and verification time.
Hosts can first call `check_reservation` with bounded decoded claims to reject
revoked callers, changed login bindings or full capacity before cryptography.
Success authenticates nothing and reserves no capacity; the final reservation
rechecks those same rules against verified claims. Preflight retains trusted clock
observations but does not install any untrusted identity or deadline.
It retains the issuer/account pair and original login start/deadline across renewal,
even after a short session lease expires. The host must still serialize verification
and commit with authority updates; equal timestamps alone do not prove freshness.
It stages changes around a synchronous
host commit callback carrying the exact proposed login record. The host must
serialize that callback and atomically commit its session/replay effects together
with that record in durable storage, or leave them unchanged on failure. Feature-gated
checked ledger restoration rejects inconsistent records/counts; it still requires
trusted atomic storage and host rollback protection. The durable adapter remains
unimplemented. The ledger itself
does not authenticate proofs, enforce startup/enrollment readiness or persist
across upgrades. `with_revocation` requires a retained receiver-wide budget for
fresh unknown-login attempts, supplied separately from proof-verification credit.
It charges before storage and retains charges on failure; exhaustion returns
`Capacity`. Live reservations and tombstone retries bypass that unknown-login
budget, while expired entries need fresh credit. This bounds new denial-state
attempts, not all ingress traffic or application callback costs. The shared session engine connects it to admission and local logout. Production
issuer/browser integration is still required for the complete logout contract below.

## Identity and trust domain

Uppercase MUST, MUST NOT and SHOULD express normative RFC 2119/RFC 8174
requirements. Configuration alone does not satisfy deployment qualification.

One login uses one fresh Ed25519 browser key. Its principal is the IC
self-authenticating principal derived from the standard Ed25519 DER public key.
Application ingress uses that principal as sender. The credential contains the
raw 32-byte browser public key; verification derives the principal and requires
equality with the authenticated runtime caller. Do not accept a stable account
principal merely because it delegated to this key. The IC's
[authentication rules](https://docs.internetcomputer.org/references/ic-interface-spec/https-interface/#authentication)
distinguish the sender identity from the final delegated signing key.
Receivers enforce caller/principal equality, not an unavailable inspection of the
ingress delegation chain. The browser adapter must not delegate or export this
login key. A delegation retaining a different stable account sender fails the
equality check even if its final signing key is the browser key.

The account subject is separate, issuer-authenticated metadata. Issuer account
authentication authorizes binding a browser key; possession of that browser key
alone cannot create a new account binding, new login start or later absolute
deadline. Renewal preserves the original key, account, start and deadline. Two
devices for one account have distinct browser principals, separate sessions and
independent revocation. Ordinary account/resource resolution uses verified
session account metadata, never caller identity as an implicit account ID.
Session records and checked authorization results MUST retain the authenticated
`(issuer, account_subject)` pair within the protected trust domain. Toko and other
consumers MUST key external account resolution on that pair, never subject alone.
Two issuers naming the same subject do not identify the same account. Account
linking requires explicit application policy; renewal MUST NOT silently replace
either component of an established session's account identity.

For this profile each receiver has one protected application trust domain: the
existing network-qualified `AudienceId` (network ID plus fleet/application ID).
The login identity is `(trust_domain, browser_principal)`; no client-selected
opaque login ID can evade revocation. A browser key is never reused for another
login. Issuers must not mint a fresh login from renewal credentials, including
after restart or binding expiry. A new login requires account authentication and
a new key. Logout revokes that browser principal across all accepted issuers in
the receiver's domain, not just one credential fingerprint. Multiple issuer
bindings cannot change the principal's original login window.

## Frozen credential shape and signed bytes

The new logical transport is `PortableCredential { claims: blob, proof }`.
`proof` is exactly one of:

- `Certified { delegation: DelegationProof, issuer_signature: IcCanisterSignatureProofV1 }`,
  using the existing bounded Root/delegation and IC canister-signature types.
- `Ed25519 { signature: blob }`, exactly 64 bytes; the public issuer key is
  obtained from protected enrollment, never from this request.

The claims blob has the exact concatenation below. Names are semantic labels,
not encoded field names. Integers are unsigned big-endian. Length/count prefixes
are u32. A principal is its raw IC bytes prefixed by byte length (at most 29).
No principal text, JSON, CBOR or Candid serializer defines these signed bytes.
Reuse the existing canonical primitive/role/scope owners when implementing this
new domain; do not change their old signed domains incidentally.

| Order | Field | Encoding |
| --- | --- | --- |
| 1 | Domain | Exact ASCII `IC-AUTH-PORTABLE-CREDENTIAL` followed by one zero byte |
| 2 | Schema | u16 value 1 |
| 3 | Mechanism | u8: 0 Certified, 1 Ed25519 |
| 4 | Network ID | 32 raw bytes from protected `AudienceId` |
| 5 | Application ID | 32 raw bytes from protected `AudienceId` |
| 6 | Issuer | Length-prefixed principal |
| 7 | Key binding ID | 32 bytes: existing `cert_hash(delegation.cert)` for Certified; SHA-256 of raw enrolled Ed25519 public key for Ed25519 |
| 8 | Browser public key | 32 raw Ed25519 bytes |
| 9 | Account subject | Length-prefixed, nonanonymous principal; issuer-scoped account identity |
| 10 | Login start | u64 Unix nanoseconds |
| 11 | Login deadline | u64 Unix nanoseconds |
| 12 | Credential issuance | u64 Unix nanoseconds |
| 13 | Admission expiry | u64 Unix nanoseconds |
| 14 | Credential nonce | 16 bytes, unique within this issuer/login |
| 15 | Grants | u32 count; each role is u32 length + ASCII bytes, followed by u32 scope count and each u32 length + ASCII scope |

No extensions, optional fields, padding, alternate integer encodings or trailing
bytes are permitted. Claims are capped at 65,536 bytes. The entire decoded
credential's variable bytes are capped at 131,072; outer Candid decoding also
needs a bounded host instruction/allocation budget. There are 1..16 role grants,
1..32 scopes per role, roles of 1..64 bytes using existing `AuthRole` grammar,
and scopes of 1..64 bytes using existing scope grammar. Roles and their scopes
must be strictly ascending by raw ASCII bytes with no duplicates. Verification
rejects noncanonical input; it never sorts or normalizes signed material.

The signed message is `SHA-256(claims_blob)` (32 bytes). Ed25519 signs/verifies
those bytes using ordinary strict Ed25519, not Ed25519ph. A future threshold
Schnorr Ed25519 issuer can sign this same 32-byte message with the same envelope
and receiver verifier; signing custody is an enrollment decision, not a different
signature encoding. It requires an explicitly approved custody policy and a qualified issuer adapter;
TEE is optional. The [enrollment contract](0.6-tee-enrollment.md) separates trusted
governance, local volatile-key lifecycle and threshold custody. Threshold batches need a new reviewed proof encoding. The
[signing comparison](0.6-portable-authentication.md#issuer-signing-alternatives-and-decision-evidence)
records per-issuance cost/latency and the pending measurement decision.
Certified mode frames this digest with the exact one-byte length of ASCII
`ic-auth-portable-credential`, those domain bytes, then the 32-byte digest, using
`domain_separated_message`. This portable IC framing domain is distinct from the
old `canic-issuer-delegated-token` domain; neither verifier accepts the other
message as a portable proof. The underlying IC witness hashes that framed message
according to the established canister-signature mechanism. The portable certified
verifier requires zero future-skew allowance for Root validity and IC certificate
time, as well as the shared strict claims clock. Root/delegation verification authenticates the exact
issuer, seed/key binding, audience, grant ceiling and certificate windows.
The mode in the claims must match both the proof variant and enrollment policy.
Key binding IDs cannot enroll a key or change its algorithm. The fingerprint
for replay is the claims digest; alternate signature/proof bytes do not produce
a new credential identity. Exact issuance retries return the same nonce/claims.

These definitions are frozen design inputs for implementation; Rust-owned
generated Candid
defines the eventual concrete transport and consumer command embedding. No
handwritten parallel browser codec. Required vectors cover both signatures over
identical semantic claims, every field changing the digest, endian/length
boundaries, duplicate/order refusals, and cross-mechanism/domain replay rejection.
Changing this schema requires an explicit design update and coordinated cut;
there is no old/new dual reader at application admission.

## Wallet origin and package boundaries

Wallet proof verification precedes portable credential issuance. The
[wallet-origin review gate](0.6-portable-authentication.md#wallet-account-authentication)
requires an explicit Ethereum message-format decision and wallet UI qualification.
ERC-4361 text with an in-house verifier is the proposed dependency-free correction;
it remains pending against the earlier no-SIWE-protocol instruction. A custom
signed domain does not authenticate the browser origin, and MetaMask's warning
is not an unbypassable origin proof or a guarantee for Solana wallets.
The [issuer package boundary](0.6-portable-authentication.md#canic-feature-selection)
is normative: receiver crates MUST NOT depend on issuer key custody/signing crates.
Canic #491 owns consumer graph/artifact qualification under feature unification.

## Time and admission rules

The deployment MUST establish a protected bound `clock_skew_ns` (Delta) on
issuer/receiver time differences for the entire login lifetime. This is not a
browser field, an assumed IC-wide guarantee or the old verifier's 60-second
grace. No production bound has been qualified yet. A host MUST refuse activation
of the volatile-reset profile without that evidence; it MUST fail closed if the
bound or monotonic-clock assumption is violated. Test fixtures may control their
clocks explicitly. Clock-skew qualification remains an acceptance prerequisite.

The protocol ceilings are 86,400 seconds per login, 60 seconds per admission
proof and 1,800 seconds per session lease. These are safety ceilings, not a
performance SLA or recommended deployment durations. Hosts may choose shorter
durations. Nanoseconds remain u64 and all additions/subtractions are checked.
No positive future-time or expiry grace is allowed in this profile:

`login_start <= issued_at <= now < admission_expiry <= login_deadline`.

A future-issued credential MUST receive a typed `NotYetValid` refusal, with no
session/replay mutation. It grants no early-admission grace. The browser may retry
the identical credential with bounded backoff while its proof and operation
deadlines remain open and its durable login generation is unchanged. It MUST NOT
mint replacement credentials in a retry loop or trust a reply's suggested delay
as permission to extend a signed deadline. Qualification MUST exercise an issuer
clock ahead of the receiver, including a proof expiring before a successful retry.

The login deadline minus login start is positive and at most the login ceiling;
admission expiry minus issuance is positive and at most the proof ceiling.
Receiver policy can impose stricter bounds. Refuse clock rollback, overflow,
wrong domain/caller, revoked login, stale authority and insufficient budget before
expensive verification where safely possible. Never trust a client time as the
clock or permit it to set authority. Each successful admission lease ends at the
minimum of requested/protected lease, login deadline, key validity and the
enrollment snapshot freshness deadline used for that admission.

Proof expiry prohibits new admissions but does not itself invalidate an existing
session. All session checks enforce the stored exclusive lease deadline, actual
caller, live generation/revocation, current key validity and current enrollment
freshness. Refreshing enrollment cannot lengthen the stored deadline or resurrect
an expired session. Refreshing a login is not a new login start. Grant narrowing,
replay, work budgets and session storage remain shared across both mechanisms.

## Logout

The logical update request and result types are fixed as follows. Canic embeds
them in its owned command surface; this does not advertise new endpoints today.

```candid
type LogoutRequest = record {};
type LogoutResult = variant {
  Revoked : record { deny_until_ns : nat64 };
  InvalidCaller;
  Unavailable : variant { Capacity; Storage; Clock; ResetPending };
};
```

The target is always the authenticated caller in the receiver's installed trust
domain. There is no request-supplied subject, issuer, deadline or proof. Require
a nonanonymous self-authenticating caller; the IC authenticates its ingress.
An inter-canister proxy does not inherit the original browser's authority.
At an issuer this operation also disables that principal's binding and renewal.
At a receiver it atomically removes all its sessions and installs a tombstone.
It does not grant any access and does not require an account lookup.

| Local state | Validation/action |
| --- | --- |
| Session exists | Authenticate caller, reserve/retain its revocation record, remove session atomically |
| No session / establishment failed or is pending | Same caller authentication; create bounded tombstone before any later admission |
| Admission proof expired | Irrelevant: no credential is submitted or verified |
| Issuer key expired/retired or enrollment stale | Still permit self-revocation using IC caller authentication |
| Tombstone exists | Return its existing deadline without extending it or adding records |
| Anonymous/non-self-authenticating caller | `InvalidCaller`, no mutation |
| No safe capacity/commit or startup not ready | Typed `Unavailable`, no false success |

A first logout MUST retain the tombstone until checked
`now + 86,400 seconds + 2 * clock_skew_ns`, covering every existing login window even
when the issuer clock is ahead and the receiver never saw the credential. One
margin covers issuer-ahead login timestamps; the other retains denial through
the signed deadline plus the uncertainty margin. All arithmetic is checked. It
MUST NOT end before a locally authenticated login deadline plus the skew margin;
an inconsistent later deadline indicates violated authority/time assumptions and
MUST fail closed rather than acknowledge an insufficient tombstone. This margin
does not permit admission before issuance or after expiry. Repeats within retention return the same
deadline. After retention, a repeat may create a new bounded tombstone, still
only denying that caller. A key holder with fresh account authentication must
use a new key for a new login; the old login cannot renew beyond its deadline.

Admission reserves one revocation slot per admitted browser principal. Logout
converts that reservation atomically, rather than competing with unknown callers.
The reservation survives session expiry through that login's absolute deadline
plus the skew margin;
retiring a short lease cannot silently remove the ability to revoke its renewal.
For absent sessions use a separately bounded pool and receiver-wide work budget;
exhaustion returns `Capacity`. Unknown-login work credit MUST be shared across
callers and endpoints and MUST remain separate from proof-verification credit.
A live admitted reservation or tombstone retry MUST NOT depend on unknown-login
credit. An expired entry no longer qualifies for this exemption. Unique principals
cannot force unlimited allocation.
Do not evict unexpired tombstones, refund spent work on normal errors, or report
`Revoked` after a failed commit. Issuer state follows the same bounded reservation
rule for admitted bindings. Logout is permitted even when new admission is off.

Lost replies mean unknown outcomes; repeating this denying-only operation is
safe. `Revoked` acknowledges local committed revocation only. It is neither an
issuer-wide broadcast nor a claim that another receiver or device logged out.
Client reports distinguish confirmed result, transport-unknown and local logout.

`Capacity` is retryable while establishment may still arrive: the browser retries
the same principal's logout with bounded backoff, concurrency and a fixed cleanup
deadline. A later successful establishment reserves revocation capacity, allowing
a subsequent logout to commit. The browser MUST cover known outstanding proofs'
remaining admission windows plus its qualified clock margin when selecting that
deadline. Proof expiry alone MUST NOT be reported as receiver revocation: admission
may have committed just before expiry, leaving a session alive. Unknown issuance,
failed issuer revocation and a lost admission reply retain explicit uncertainty.
The [browser cleanup contract](../browser-client.md#planned-06-logout-retries)
defines key retention, terminal reporting and the bounded retry limit.

Proofless means no credential is required, not that the caller is unauthenticated.
An attacker can still create many valid principals. Admitted-login reservations
MUST be isolated from the unknown-caller pool; that pool MUST have a fixed cap
and receiver-wide work budget. Unknown callers can exhaust it, producing typed
unavailability; no fairness or Sybil resistance is claimed. This cannot consume
reserved logout capacity or evict live tombstones.

Optional expired-credential validation is not selected for 0.6. It could provide
evidence for capacity allocation, but adds cryptographic denial-of-service work
and a separate contract for retired keys, historical authority and expiry. It
MUST NOT be implemented by skipping ordinary verifier checks or trusting a
client-supplied deadline. The existing conservative maximum-lifetime tombstone
avoids that dependency. Any future evidence-bearing logout requires its own
bounded verifier and capacity qualification; it must never shorten a tombstone.

## Ordering and in-flight work

Issuer logout linearizes at the atomic commit marking the browser binding
revoked. Issuance captures binding/authority generation before asynchronous work,
then rechecks live generation, revocation, fixed login window and key policy in
the same synchronous message segment that publishes/commits the credential.
A revoked/stale callback discards its result. Preparation intent is not issuance
authority. Certified retrieval must not publish previously uncommitted preparation
after revocation; already committed/retrievable proofs count as outstanding proofs
and remain bounded at uninformed receivers. Never rely on canceling a browser
promise to cancel a server operation.

Receiver logout linearizes at session removal plus tombstone commit. Admission
and logout must have a single serializable transaction boundary; no await between
revocation check and session commit. Logout first means later admission fails;
admission first means logout removes it. Exact admission retries after logout
must refuse. Checked session handles cannot survive an await as authority.

For application workflows, recheck the captured session/login generation and
current policy after every await before any new privileged mutation or outbound
effect. Work already dispatched before logout may finish externally; irrevocable
effects are not rolled back. Reconciliation/compensation of those effects follows
the application's previously authorized operation, without granting new user
authority. The endpoint guard alone cannot enforce this across callbacks; Canic
supplies recheck support and Toko owns workflow effect boundaries. See the IC's
[inter-canister ordering guidance](https://docs.internetcomputer.org/guides/security/inter-canister-calls/).

## Enrollment and restoration

The installed enrollment authority is Canic Root for a Canic domain; standalone
hosts explicitly install their own equivalent authority. Browser fields cannot
select or replace it. Snapshots are complete for the receiver's domain and bind
authority identity, receiver principal, boot challenge, u64 revision, u64 authority
generation, issue time, freshness deadline, entries and revoked key IDs. Entries
bind issuer, algorithm, key/binding ID, key bytes, validity, grants and deployment
approval digest. Authentication is an IC-authenticated call/response to the exact
installed authority, not an arbitrary relayed signed document. Other transports
require a separately reviewed contract and are not supported by this profile.

Freshness is at most 3,600 seconds from authority issuance and cannot exceed
an entry's deployment approval deadline for that entry. The authority chooses a
shorter qualified operational interval when necessary. Both old sessions and new
admissions refuse stale enrollment. Refresh/control-plane traffic is administrative
and outside the user request path; its frequency and costs must be measured.
This creates a bounded partition-availability tradeoff, not free offline trust.

Root is therefore a fleet-wide liveness dependency for both proof mechanisms:
every receiver needs it at boot/upgrade and before its at-most-hourly enrollment
expires. Receiver-pulled refresh with bounded randomized jitter and retry backoff
SHOULD be the default; schedule refresh ahead of expiry and never jitter past it.
Root MUST NOT require synchronous fleet-wide push completion for routine refresh.
Urgent revocation hints may accelerate pulls but cannot extend validity. A Root
outage drill MUST show boot remaining closed, existing sessions/admissions refusing
after enrollment expiry, bounded retry load, and recovery with monotonic revisions
without extending old leases or reviving revoked keys/logins.

Revisions strictly increase on every new snapshot, including a freshness-only
refresh. An exact repeat of the same revision/digest is idempotent; a lower
revision or same revision with different bytes refuses. Generations never decrease
and increase for revocation, key/algorithm/grant changes or reduced validity.
Refresh alone may preserve generation. A change of generation invalidates old
sessions; increasing snapshot freshness alone cannot extend their stored leases.
Key revocation is terminal for that key ID in this domain: recovery enrolls a new
key, never re-enables the old one. Overflow refuses, never wraps.

Install snapshot, high-water revision/generation and invalidations atomically.
Every install/post-upgrade/recovery starts auth closed, generates a fresh boot
challenge and requests a fresh snapshot for that receiver from its installed
authority before serving sessions. The authority returns its current revision
at response commit, not a client-requested historical revision. The response must
match the outstanding boot challenge and local receipt deadline. Normal upgrades
also compare retained high-water marks. Backup restoration cannot trust those
old marks alone: the fresh authenticated authority response is mandatory.
An unavailable authority keeps auth closed; no fallback to an old signed snapshot.
No local snapshot refresh can undo a tombstone or reset a login cutoff.

The enrollment authority must itself retain monotonic revision/revocation state.
Its recovery from stale backup requires a new trust epoch/bootstrap at consumers;
it must not serve old authority under the old identity as though current. This is
an operator-controlled recovery boundary, not a runtime migration fallback.

| Host event/profile | Required behavior |
| --- | --- |
| Persistent normal upgrade with complete transaction state | Restore checked sessions, replay, tombstones, login floor and authority high-water marks; authenticate fresh boot snapshot before opening; retained sessions still obey original deadlines |
| Memory normal upgrade/reset | Drop sessions/replay/tombstones; set trusted `min_login_started_at_ns = checked(boot_time + clock_skew_ns + 1)` and existing proof issuance floor; authenticate fresh boot snapshot; reject every pre-reset login, including freshly issued renewals |
| Either profile restored from backup, incomplete state, or storage mode change | Invalidate all sessions/bindings for this host, use the same new login-start and proof floors, and authenticate fresh boot snapshot; never revive backup sessions/tombstones as current authority |
| Issuer normal persistent upgrade | Restore binding windows/revocations and issuance intents; recheck authority before completing pending issuance |
| Issuer binding-state loss or rollback recovery | Disable every pre-reset binding; require new account authentication and browser key; old browser key alone cannot recreate binding |

`PortableClaimsContext::advance_reset_floors(clock_skew_ns)` supplies the checked
calculation using `now_ns` as trusted boot time. It preserves stronger existing
floors and leaves both unchanged on overflow. Hosts MUST retain the resulting
policy atomically with state invalidation; mutating a temporary request context
and discarding it does not implement reset protection. The helper neither
qualifies clock/skew inputs nor opens the startup gate. A persistent normal
upgrade with complete retained state does not call this state-loss helper.

Login-start floors are monotonic during a host lifetime; memory reset relies on
trusted IC monotonic time, checked arithmetic and immutable issuer-signed login
start. The skew margin MUST cover an issuer clock ahead at reset; overflow or
unavailable/rolled-back time MUST refuse. A slower issuer may need to wait before
it can issue a fresh login beyond this floor. This adds a login-start floor beyond
the current proof-issuance floor: a renewed old login cannot bypass reset merely
by carrying a new proof timestamp. Memory mode therefore needs no durable session
decoder or logout tombstones, but forces a fresh login after reset. The browser
must not silently fall back to renewal. Standalone identity-service account data
is not disposable under these application-session reset rules.

This is a deployment cost: each memory-mode receiver upgrade forces its returning
users to authenticate their accounts again, potentially including a wallet
signature prompt. Frequent upgrades can therefore create repeated login friction.
Persistent mode avoids this on complete normal upgrades, but still obeys the
backup/mode-change reset rule. Hosts MUST document that UX choice.

## Mandatory adversarial cases

Qualify each mechanism against two device keys for one account; wrong stable
delegated caller; absent-session logout after proof expiry and retired issuer key;
revocation capacity exhaustion without false success; logout before/after admission;
issuance paused across logout; app callbacks attempting new post-logout effects;
old enrollment after revocation followed by normal restart and backup restore;
memory reset plus fresh renewal of an old login; and authority refresh without
lease extension. Browser tests must crash after durable logout but before fan-out
and resume suspended tabs. Inspect exact committed outcomes, not just UI state.
Also qualify issuer-ahead reset clocks, slow-issuer fresh login, skew-bound
failure/overflow, logout just before the maximum login deadline, renewal while
issuer logout is unreachable, and unknown-principal floods preserving admitted
logout reservations. Each uppercase requirement needs an explicit acceptance
case; no deployment is qualified solely by passing software protocol tests.
