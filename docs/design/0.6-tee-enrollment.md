# 0.6 issuer enrollment and optional TEE custody

This companion to the [portable authentication design](0.6-portable-authentication.md)
and [protocol contract](0.6-auth-protocol.md) defines issuer trust and key lifecycle.
The 2026-10-14 simplification supersedes the earlier universal TEE/controller gate.
These are design requirements, not an implemented issuer service or attestation
collector. Canic owns deployment and enrollment under
[#491](https://github.com/dragginzgame/canic/issues/491); Auth owns reusable proof
and session machinery.
MUST and SHOULD express normative requirements.

## Trust the issuer's governance explicitly

Root approves which issuers may authenticate accounts and issue which grants.
Standalone Auth hosts install their own enrollment authority; no Canic dependency
is required. Issuer and enrollment-authority controllers are trusted to administer
those permissions correctly, including their upstream governance/controller chain.

This trust applies to both local signing and chain-key signing. Controllers can
replace issuer code to authorize unwanted credentials or request chain-key
signatures. Threshold signing prevents extraction of a complete private key; it
does not prevent malicious application administration. A copied local key adds
an off-network signing risk until receivers stop accepting that key.

Production approval MUST identify the trusted governance and permitted issuer
scope. There is no blanket requirement for controllerless deployments, no ban on
externally held controllers, and no requirement to prove the absence of every
management-call path. Applications needing stronger governance guarantees must
state and qualify them separately. TEE hosting does not remove controller trust.

## Simple local-key lifecycle

1. The issuer generates an Ed25519 key using IC `raw_rand` and established key
   primitives. Keep the secret only in heap state, with no stable-memory export,
   upgrade serialization, logs or client responses.
2. The issuer registers its public key with Root through an authenticated IC
   exchange. Root checks the issuer identity, allowed grants and custody policy,
   binds the key to this trust domain and a finite validity window, and approves
   it atomically. A browser-supplied key cannot enroll itself.
3. Where enrollment must be portable, Root chain-key-signs the issuer/key
   authorization. Receivers authenticate that authorization at enrollment or
   rotation and cache the protected result. Hosts already using authenticated
   Root enrollment snapshots need not add a second signature to those calls.
   No Root/BLS verification or issuer ICC is added to each Ed25519 user admission.
4. Issuers sign short-lived user credentials locally. Receivers use the enrolled
   key and the shared session engine's admission, replay and revocation rules.
5. Every issuer code upgrade clears the old heap key and generates a fresh key.
   The new deployment cannot issue credentials until Root approves it. Planned
   upgrades retire the old enrollment first; recovery/restoration MUST NOT revive
   an old key. Hosts must explicitly disable any heap-preservation/serialization
   path that would defeat this lifecycle.

Registration MUST bind the responding issuer, domain, public key and current
Root challenge; key possession and authenticated caller checks must precede
approval. Approval also records custody policy, allowed grants, validity and
monotonic revision/generation. The former TEE-specific challenge encoding is
withdrawn as a universal contract: no registration implementation exists yet.
Freeze and test the exact registration/authorization encoding with its producer
and consumer before adding an accepting endpoint.

Rotation is a lifecycle safeguard, not erasure of copies. Known or suspected key
disclosure requires retirement. Controller changes require renewed governance
approval; the authority retires the key if custody is uncertain. A snapshot may
contain heap secrets. Keep snapshots restricted to trusted controllers and do not
export live-key snapshots. Taking a snapshot alone is not proof of disclosure or
an automatic retirement event; snapshot access follows the trusted maintenance
policy. Restored snapshots never restore enrollment authority for an old key.
See the [IC management specification](https://docs.internetcomputer.org/references/ic-interface-spec/management-canister/).

## Custody choices, independent of the receiver flow

| Custody policy | What must be trusted or qualified |
| --- | --- |
| Local volatile key on an ordinary subnet | Governance and the deployment's replica/operator confidentiality assumptions; explicit operator approval, no TEE claim |
| Local volatile key with TEE protection | Same governance trust, plus qualified confidential execution covering the issuer's replicas and key lifecycle |
| Threshold Schnorr Ed25519 | Governance and the threshold service; no complete issuer key in heap, but a signing call for each credential unless a separate batching protocol is designed |

IC randomness supplies unpredictable entropy; it does not hide the resulting
secret from replicas executing the canister. The ordinary-subnet local-key
profile MUST acknowledge that assumption explicitly. It is not an automatic
fallback when a deployment configured to require TEE loses its assurance.
See [IC randomness](https://docs.internetcomputer.org/guides/backends/randomness/).

TEE qualification is required only for a TEE assurance claim. The enrollment
owner must establish the issuer/subnet/replica binding, accepted platform
measurements and freshness, and safe state transfer/recovery. GuestOS attestation
alone does not directly bind our canister key and Wasm. If the needed evidence is
unavailable, refuse that custody profile; software tests cannot substitute for it.
No proposal watcher is mandatory for all deployments. A profile promising
suspension before NNS/platform changes must demonstrate how it achieves that;
otherwise report detection and revocation as eventual, bounded by enrollment
expiry. See [node infrastructure](https://docs.internetcomputer.org/concepts/node-infrastructure/).

## Revocation, sessions and acceptance

The protocol's finite key/enrollment validity, monotonic revisions and authority
generations remain mandatory. Retirement is terminal for a key ID. Refresh cannot
undo revocation or extend an existing session lease. Receivers invalidate affected
sessions when retirement/generation changes are installed; uninformed receivers
may continue within the documented validity window. An upgrade is not instant
fleet-wide logout. Enrollment outages fail closed at the existing deadlines.

Issuer heap-key storage is independent of receiver session storage: receivers
still choose volatile or persistent sessions. Persistence never overrides key
retirement, authority expiry or the protocol's reset/restore rules.

Qualification must cover authenticated registration, unauthorized issuer/key
substitution, wrong grants/domain, expiry, revision rollback, fresh-key upgrade,
old-key restore refusal, outage/rotation propagation and affected session checks.
Run real Ed25519 and certified proof tests locally without TEE; keep hardware
assurance tests separate. Compare full issuance, enrollment/rotation, admission,
renewal and ordinary-call costs before choosing custody for production. No
custody profile changes wallet origin binding or browser logout limitations.
